# Soyuz implementation plan

Prepared before implementation on 2026-10-02.

## Current-state findings

- The Soyuz `main` checkout is an initial commit with only a placeholder README and license. There is no existing runtime, API, schema, or test suite to preserve.
- `CyanAutomation/kaseki-agent` has default branch `main`, observed at commit [`adb830d`](https://github.com/CyanAutomation/kaseki-agent/commit/adb830d349642f8f9bf06f491333d94c4c4a6940) (v1.147.2). Its [README](https://github.com/CyanAutomation/kaseki-agent/blob/main/README.md) describes a Docker-backed runner; its [lifecycle guide](https://github.com/CyanAutomation/kaseki-agent/blob/main/docs/KASEKI-AGENT-LIFECYCLE-DIAGRAMS.md) separates queueing, startup, execution, and terminal outcomes.
- Kaseki's [RunRequestSchema](https://github.com/CyanAutomation/kaseki-agent/blob/main/src/kaseki-api-types.ts) validates `repoUrl`, `ref`, `projectName`, prompt, file allowlists, diff limit, validation and cleanup settings, goal/scouting/check/evaluation controls, task and publish modes, startup checks, webhook configuration, tracing, idempotency UUID, and timeout. It defaults `ref` to `main`; the API defaults `publishMode` to `pr`. The current request body accepts camelCase and normalizes selected snake_case aliases.
- Kaseki's [API route](https://github.com/CyanAutomation/kaseki-agent/blob/main/src/kaseki-api-routes.ts) runs execution-context safety admission before idempotency and scheduler submission. Existing callers receive `kaseki-N` IDs. Idempotent replay returns the existing response (HTTP 200); a fresh run returns 202. Its internal scheduler owns Docker execution and currently classifies cancellation as a failed job with `failureClass: cancelled`; Soyuz will expose cancellation intent and confirmation as a distinct external lifecycle state.
- Kaseki's scheduler persists a queued job and its restart ownership claim before it starts processing the local queue. On restart it can recover claimed queued jobs, while jobs persisted as running are finalized as `failed` with `failureClass: api_restart`. A later adapter can therefore acknowledge a pulled message after durable local admission, but it must add a durable Soyuz run ID mapping because the current scheduler allocates `kaseki-N` IDs. Kaseki's structured event snapshot is derived from local `progress.jsonl`, live events, and sometimes Docker log tails; those execution logs remain on the Kaseki side.
- **Design refinement after the initial plan:** Queue redelivery can race across hosts. A host claim is therefore a real lifecycle step, not an execution detail. Soyuz records a time-limited `claimed` owner before Kaseki persists/schedules locally; the Kaseki adapter must not execute until its `started` callback changes that claim to `running`.
- Cloudflare's current official documentation says Queues deliver at least once, so consumers must tolerate duplicates ([delivery guarantees](https://developers.cloudflare.com/queues/reference/delivery-guarantees/)). HTTP pull consumers are external HTTP clients that explicitly pull and acknowledge or retry messages, and need Queue read/write permissions ([pull consumers](https://developers.cloudflare.com/queues/configuration/pull-consumers/)). D1 `batch()` is transactional: its prepared statements run sequentially and a failing statement rolls back the batch ([D1 database API](https://developers.cloudflare.com/d1/worker-api/d1-database/)). Cloudflare currently recommends the Workers Vitest plugin for Worker tests ([Vitest integration](https://developers.cloudflare.com/workers/testing/vitest-integration/)); Wrangler's `types` command generates runtime and binding types ([Wrangler commands](https://developers.cloudflare.com/workers/wrangler/commands/)).

## Proposed implementation

1. **Architecture.** Use a native module Worker router and explicit environment bindings. Soyuz remains the API, admission, canonical-state, and event service; the separately deployed Kaseki host remains the execution service. Keep contracts local and versioned; do not import Kaseki source.
2. **D1 schema.** Create `runs` and append-only `run_events`. Keep searchable lifecycle, repository, mode, timestamps, worker/claim lease, failure, cancellation, idempotency, and trace fields in `runs`; store the normalized Kaseki request and small terminal summary as JSON. Add unique idempotency identity plus status/date and event indexes. Timestamps are ISO UTC.
3. **Public API.** Implement public health plus authenticated `POST/GET /v1/runs`, `GET /v1/runs/:id`, and `POST /v1/runs/:id/cancel`. Use JSON `data` success envelopes, stable error codes, a request ID, bounded list pagination, and UUID run IDs. Add worker-authenticated status reads, a compare-and-set claim callback, and callbacks for started, operational events, completed, failed, and cancelled.
4. **Request contract.** Preserve Kaseki's useful execution options and names, including validation/allowlist, goal/scouting/evaluation, modes, startup checks, and timeout. Keep the Kaseki-compatible `ref: main` and `publishMode: pr` defaults. V1 deliberately omits `webhookConfig`: moving caller webhook secrets through both D1 and Queue needs a separate secret-handling and delivery ownership design. Soyuz validates shape only; Kaseki retains its existing safety/admission checks.
5. **Queue contract.** Publish `{ contractVersion: "1", runId, createdAt, correlationId, request }` to a Queue producer binding. The message is a transport DTO, not a D1 row. Do not add a `/next-job` route; configure HTTP pull on the Cloudflare Queue for the external Kaseki consumer.
6. **State machine.** Centralize transitions across `admitting`, `queued`, `claimed`, `running`, `cancel_requested`, `cancelled`, `completed`, `failed`, and `admission_failed`. A short-lived D1 claim is required before local scheduling because at-least-once Queue delivery can reach two hosts before either reports start. The one-minute reconciler expires abandoned claims and republishes the same run ID. Worker callbacks are idempotent by stable callback/event IDs.
7. **Authentication.** Keep unauthenticated health separate from client and worker bearer tokens (`CLIENT_API_TOKEN`, `WORKER_API_TOKEN`). Compare fixed-size token digests in constant time. Read secrets from Cloudflare bindings or ignored local `.dev.vars`; never commit tokens.
8. **Idempotency.** Accept Kaseki's UUID `idempotencyKey` and the matching `Idempotency-Key` header. Persist a SHA-256 fingerprint of the normalized execution request. Same key plus same fingerprint returns the existing run; same key with different content returns 409. Generate UUIDv7 run IDs from the current millisecond timestamp and Workers' built-in Web Crypto random bytes; callers treat them as opaque instead of relying on `kaseki-N`.
9. **D1/Queue consistency.** Insert an `admitting` row and event, call `Queue.send()`, then transactionally set `queued` and append its event. A send exception has an ambiguous outcome, so keep the run `admitting` and retry the same run ID; after five failed attempts, set `admission_failed`. A one-minute scheduled reconciler retries stale `admitting` rows and reclaims expired `claimed` rows using the same run ID. Kaseki must not acknowledge while admission is incomplete and must wait for the started callback before execution. Duplicate messages are expected. A cancellation can race with publication; the worker sees terminal state and safely skips it.
10. **Testing.** Use Cloudflare's Vitest integration with a real local D1 binding for route/state persistence and a queue test double to inject send success/failure. Cover request validation/auth, admission and reconciliation, idempotent replay/key conflict, competing claims, expired claims, transitions and cancellation races, callback retries, event de-duplication, list/get/404, and separate client/worker trust.
11. **Explicit non-goals.** Do not modify Kaseki, run Docker, clone repositories, install project dependencies as part of a run, implement artifacts/R2, UI, RBAC, billing, streaming, GitHub publishing, or migrate Kaseki's execution safety gate. The follow-up document will specify the Kaseki host work and queue acknowledgement point.
